# Web console internationalization

The console ships `en` (English) and `zh-CN` (Simplified Chinese), with no build step or
third-party translation dependency. This applies to the web UI; CLI output, API payloads,
server error details, strategy-provided descriptions and original event messages retain
their source text.

## Choosing a language

Use **Settings → Appearance → Language**. The setting is stored independently of trading
configuration in `localStorage['futu_algo.locale']`. An explicit `?lang=en` or `?lang=zh-CN`
before the URL hash overrides the preference for that URL. This also provides a fallback
when browser storage is blocked. Otherwise the saved preference wins, followed by browser
language detection (`zh-CN`, `zh-SG`, `zh-Hans*`, or `zh`), then English.

Switching language reloads the same route so module-level labels and canvas charts are
rebuilt consistently. Unsaved YAML edits require confirmation before switching. Other
unsaved form inputs reset on reload. This does not restart the backend or change trading
configuration. Dates and times retain the existing Hong Kong exchange timezone and
unambiguous numeric layout; numbers, compact quantities and relative times use `Intl`.

## Adding UI messages

Import `t as translate` from `js/i18n.js` and translate **at the display boundary**:

```js
translate('Settings');
translate('Open the {0} chart', { 0: symbol });
```

English source messages are the lookup keys and the fallback text. Add the matching entry
to `js/locales/zh-CN.js`. Use full messages with named or numbered placeholders for dynamic
text rather than concatenating translated fragments. Placeholders can be reordered in a
translation. The renderer continues to use `textContent`, never HTML interpolation.

Translate labels, not option values, API field names, enum comparisons, routes, CSS classes,
stock symbols, user configuration or arbitrary log content. Known status enums are
translated only where displayed. Static HTML uses `data-i18n`, `data-i18n-title` and
`data-i18n-aria-label`, initialized by `localizeShell()` at boot.

Screener field and pattern names have display translations in `js/locales/zh-CN-screener.js`.
For a custom screener preset, add optional `labels` and `descriptions` by locale in the YAML:

```yaml
screener:
  presets:
    my_screen:
      description: My English description
      labels: {zh-CN: 我的选股条件}
      descriptions: {zh-CN: 中文条件说明}
      filters: [{kind: simple, field: CUR_PRICE, min: 10}]
```

Preset IDs, filter fields, result keys and CSV headers remain stable. If a locale is absent,
the console uses a built-in translation when available, followed by the original text.

## Adding a language

1. Create another `js/locales/<locale>.js` exporting a message dictionary.
2. Import it in `js/i18n.js` and add it to `catalogs` and the native-language label to `LOCALES`.
3. Add any regional aliases to `normalizeLocale()` and any required `Intl` mapping.
4. Extend browser tests to cover the locale. Missing messages fall back to English.

## Verification

```sh
node --test tests/js/i18n.test.mjs
python -m pytest tests/test_web.py
python -m pytest tests/e2e/test_console.py -m e2e
```

The Node tests check language selection, storage failure, interpolation, missing messages,
duplicate catalog keys, placeholder parity and explicit message coverage. Browser tests
cover all nine routes, mobile layouts, backtests in both languages and persistence with
unsaved-config protection. Install the project's `dev` and `e2e` dependencies; browser tests
also need Chromium, or `FUTU_ALGO_CHROMIUM` pointing to a local Chromium-compatible browser.
